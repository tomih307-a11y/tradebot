# tradebot — استراتيجية «تسلسل عبور الصفر لـ PMO»

بوت لعقود MEXC الآجلة. الاستراتيجية وحدة مستقلة تُختار من `config.toml` (`[general] strategy = "pmo_zero_cross"`).

## التشغيل
```bash
pip install -r requirements.txt
python -m pytest tests -q                                   # الاختبارات الإلزامية
python -m tradebot backtest                                  # الفترة والعملات من config.toml
python -m tradebot backtest --start 2025-01-01T00:00:00Z --end 2025-06-01T00:00:00Z --symbols BTC_USDT,ETH_USDT
python -m tradebot compare-tv --file tv_btc_15m.csv --tf Min15   # مقارنة PMO/SIGNAL مع TradingView (CSV: time,pmo,signal)
export MEXC_API_KEY=... MEXC_API_SECRET=...                   # للحي الحقيقي فقط
python -m tradebot live                                      # trading.dry_run=true افتراضياً
```
المخرجات في `reports/`: `pmo_report.md`، `pmo_trades.csv` (كل الحقول)، `pmo_rejected.csv`، `last_backtest_cells.json` (يقرؤها التنبيه الحي).

## ما تغيّر في النسخة 2 من المواصفات
- **المهلة الديناميكية** `WAIT_DEADLINE` بدل المهلة الثابتة (`[exits] min_wait_1h / wait_eta_mult / max_wait_1h_cap`)، تُحسب عند الدخول وتُعاد عند كل شمعة ساعة مغلقة، وتُسجَّل كل قيمة في CSV.
- **تصنيف الحالة بالميل أولاً** (ميل الساعة × ميل الـ4س = 4 حالات) ثم الموقع كمستوى ثانٍ.
- **أولوية الدخول:** عدد الفريمات التي ميلها مع الصفقة، ثم المرحلة الابتدائية، ثم أقل ETA، ثم السيولة.
- `trail.mult_2` الافتراضي أصبح 1.5. تقارير جديدة: دقة ETA، توزيع الربح على المراحل، مقارنة المهلة (مع وضع «بدون مهلة»)، وسعر كل انتقال.

## قرارات تفسيرية (راجعها)
0. **المهلة:** «رقم الشمعة» = رقم شمعة 15د المطلق (`ts // 900`). السقف `max_wait_1h_cap` يحدّ مدة الانتظار المضافة. إعادة الحساب تستبدل القيمة السابقة (قد تقصّرها). الخروج عندما يتجاوز رقم الشمعة `WAIT_DEADLINE` (أي بعد 16 شمعة كاملة على الأقل، وليس عند الـ16).
0b. **دقة ETA:** الخطأ = (زمن العبور الفعلي − ETA المتوقع) بشموع الساعة، على الصفقات التي بدأت WAIT_1H وكان ETA منتهياً وعبرت فعلاً. المقياس متحيز لأن الصفقات التي خرجت قبل العبور لا تُقيَّم.
0c. **توزيع الربح:** حركة السعر لصالح الصفقة بين أسعار إغلاق الانتقالات؛ MFE كل مرحلة = أفضل سعر في شموع المرحلة نسبةً إلى سعر بدايتها.
1. `stop_loss_pct` نسبة من **سعر** الدخول (وليس من الهامش). `trade_size_usdt` هو **الهامش**؛ القيمة الاسمية = الهامش × الرافعة.
2. وقف التعادل لا يُطبَّق إلا إذا تجاوزه السعر الحالي (`trail.breakeven_requires_protective`)؛ وإلا يقع فوق السعر في اللونق ويُضرب في الشمعة التالية، خصوصاً للدخول المباشر في WAIT_4H. اجعله `false` للتطبيق الحرفي.
3. الدخول المباشر في RIDE يطبّق قاعدة المرحلة 2 فقط (بدون وقف تعادل) لأن النص لا يذكره هناك.
4. سبب الخروج بالوقف يُحدَّد بمرحلة القاعدة التي رفعت الوقف آخر مرة (0 = لم يتحرك = وقف ابتدائي).
5. نسبة «عبرت الساعة/الـ4س» في الجداول تحسب الصفقات التي بدأت متجاوزة الفريم كـ«عبرت» (0 شمعة)؛ ولذلك يُعرض أيضاً المقياس الشرطي (على الصفقات التي كانت تنتظر العبور فعلاً) في «مقاييس التسلسل».
6. «القيمة المتوقعة» = متوسط العائد الصافي ÷ نسبة الوقف الابتدائي (وحدات R). «MFE المحتفظ» = Σ العائد الإجمالي ÷ Σ MFE.
7. التمويل: التسويات الواقعة بين وقت الدخول ووقت الخروج (حدّان مستبعدان)؛ من تاريخ MEXC إن غطّى الفترة وإلا بالقيمة الثابتة كل 8 ساعات.
8. الصفقات المفتوحة بنهاية البيانات تُغلق بسعر آخر إغلاق بسبب `END_OF_DATA` وتُستبعد من الإحصاءات.
9. معيار «القرار» في المقارنات: يُقبل المتغير إذا كان متوسط عائد التحقق > 0 (مع ≥ `min_sample` صفقة) ومتوسط الاختيار ≥ الأساس.
10. الحي: سعر التنفيذ الفعلي للخروج بوقف MEXC يُقدَّر بسعر الوقف (أو الافتتاح عند الفجوة) لأن سجل الأوامر لا يُقرأ.

## مصدر البيانات: MEXC فقط
- البوت يقرأ ويتداول على MEXC، فبياناتها هي المرجع الوحيد.
- مقارنة 2026-10-12 مع TradingView: `close` و`realClose` متطابقان في MEXC. شموع TradingView تختلف قليلاً (فتح شمعة 06:00 مثلاً 83,893.4 مقابل 83,981.0 عند MEXC). ولا يمكن الجزم بأن الفرق من البيانات وليس من الصيغة.
- ملاحظة: في واجهة MEXC تفتح كل شمعة بسعر إغلاق السابقة تماماً، فلا تظهر فجوات افتتاح في الباكتست، وقد يكون ذلك متفائلاً قليلاً بشأن تنفيذ الوقف عند الفجوات.

## نتائج الباكتست الحقيقي (20 أبريل → 11 أكتوبر 2026، كل عقود MEXC USDT: 1088)
- **الاتجاه الأصلي:** 228,922 صفقة، متوسط العائد الصافي −0.19% (اختيار) و−0.22% (تحقق). لا مضاعف وقف ولا فلتر نجح.
- **الإشارة وحدها** (بدون وقف، قبل التكاليف): −0.02% إلى −0.09% بعد 15د…24س؛ العكس +0.02% إلى +0.09% قبل التكاليف.
- **العكسي** (دراسة مستقلة `tools/reverse_study.py`): 18 نسخة كلها سالبة في التحقق بعد التكاليف (0.12% رسوم+انزلاق).
- التقارير الكاملة على فروع GitHub: `backtest-results` (8 عملات) و`backtest-results-all` (كل العقود) و`audit-results` و`reverse-results` و`tv-compare`.
- **الخلاصة:** لا ميزة ربحية بهذه القواعد في هذه الفترة (6 أشهر، نظام سوق واحد). لا تداول بمال حقيقي؛ أبقِ `dry_run = true`.

## وحدة توصيات قناة Telegram (`telegram_signals`) — ورقية فقط
- تقرأ قناة **عامة** من صفحتها العامة (بدون أي صلاحية على حسابك)، وتحلل التوصيات (عملة، اتجاه، دخول، وقف، أهداف، رافعة).
- الحدود (من `config.toml`): هامش **10% من الرصيد** لكل صفقة، **صفقتان متزامنتان** كحد أقصى. الهامش معزول، فأقصى خسارة للصفقة = هامشها.
- الوقف بقاعدة القناة (إغلاق شمعة 4 ساعات) أو `stop_mode = "exchange"`. المحاكاة تأخذ التصفية والرسوم والانزلاق بالحسبان.
- فحوص صلاحية فقط (ليست حدود مخاطرة): تجاهل التوصية القديمة، أو التي فات سعرها، أو عملة غير متاحة، أو لا يمكن تحديد حجمها.
- **التنفيذ الحقيقي غير مفعّل** في الكود (`trading.dry_run` يجب أن يبقى true)؛ ينتظر موافقة صريحة.
- الاختبار التاريخي: `python -m tradebot --strategy telegram_signals backtest --history result.json`. الدليل: `docs/WINDOWS_TELEGRAM.md`.

## غير مُتحقَّق منه
- لم تتوفر شبكة إلى MEXC أثناء التطوير: **لم يُختبر أي نداء حقيقي** (الشموع، التمويل، الأوامر، أوامر الوقف `stoporder/*`). مسارات وحقول الجزء الخاص في `mexc/client.py` مكتوبة من الوثائق العامة وتحتاج مراجعة بحجم صغير و`dry_run=true` أولاً.
- اختبار TradingView (رقم 1) يحتاج ملفات CSV منك: `tests/data/tv_btc_15m.csv` و`tv_btc_60m.csv` (الأعمدة `time,pmo,signal`؛ `time` = epoch ثوانٍ لفتح الشمعة) + شموع BTC المخزنة في `data/cache/` (تُنشأ بتشغيل الباكتست).
- رسم Taker الافتراضي (0.04%) يجب أن تطابقه مع حسابك.
